## 2. ADO SecurityRoles API Surface

The SecurityRoles API is a preview API (`7.1-preview.1`) accessed at:

```
GET  /_apis/securityroles/scopes/{scopeId}/roleassignments/resources/{resourceId}
POST /_apis/securityroles/scopes/{scopeId}/roleassignments/resources/{resourceId}
DELETE /_apis/securityroles/scopes/{scopeId}/roleassignments/resources/{resourceId}
GET  /_apis/securityroles/scopes/{scopeId}/roledefinitions
```

**Note:** This API is not in the official `github.com/microsoft/azure-devops-go-api` SDK; the provider uses a hand-rolled client in `azuredevops/utils/sdk/securityroles/`.

```
SecurityRoleAssignment {
    identity          SecurityRoleIdentity  { displayName, id, uniqueName }
```

#### Writable gap detail

| Gap | Verdict | Rationale |
|---|---|---|
| All absent fields | **Resolved (omit or non-writable)** | All absent fields are non-writable response metadata or computed display values. None require user input. `access` / `accessDisplayName` could optionally be surfaced as computed attributes but provide negligible operational value. |
| `access` (assigned vs inherited) | **Deferred** | Could be surfaced as a computed field to distinguish explicit vs inherited assignments; low priority |

#### Resource ID strategy

The resource generates a random UUID ID (`sra-<uuid>`). This is because there is no stable server-side ID for a role assignment (it is keyed by scope + resourceId + identityId). The ID is non-deterministic across plan/apply cycles; this is a known limitation.

## 6. Known ADO API Limitations

| Limitation | Impact |
|---|---|
| No stable server-side assignment ID | Resource ID is a client-generated UUID; drift detection is based on scope + resource_id + identity_id lookup |
| `access = "inherited"` assignments cannot be deleted | Provider's Delete calls the API but inherited assignments may reappear; provider does not currently detect this |
| API is `7.1-preview.1` | Preview APIs can change without notice; stable release expected but not guaranteed |
