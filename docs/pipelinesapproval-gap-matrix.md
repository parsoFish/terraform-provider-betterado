## Overview

The ADO Pipelines Approvals API (`_apis/pipelines/approvals`) manages approval decisions on pending pipeline run checks. When a pipeline run reaches a stage gated by an approval check, ADO creates an `Approval` object with a generated UUID and status `pending`. An authorized approver must then approve or reject the run before it can proceed.

**Key characteristic:** Approval IDs are **ephemeral** — they are generated per pipeline run and are bound to that specific run. They cannot be imported into Terraform state, because the next pipeline run will generate a new approval ID. The approval decision (`approve`/`reject` + optional comment) is the **sole declarative state** that betterado can manage.

### When approval decisions are needed

Approval decisions are needed in CI/CD pipelines that use environment protection rules (or other check types backed by the Approval check type) to gate deployment stages on human sign-off. betterado's `betterado_pipeline_approval` resource allows Terraform to programmatically approve or reject a pending approval as part of an automated workflow (e.g. integration test pipelines that self-approve).

## Resource type coverage

| ADO API | betterado resource type | Role |
|---|---|---|
| `GET /approvals/{approvalId}` | — | Read single approval (used internally) |
| `GET /approvals` (query by IDs) | `betterado_pipeline_approvals` (data source) | Lists pending approvals for a project |
| `PATCH /approvals` | `betterado_pipeline_approval` (resource) | Manages the approval decision (approve/reject + comment) |

### `betterado_pipeline_approval` (resource)

Manages a single pipeline approval decision. Given an ephemeral `approval_id` (obtained from the `betterado_pipeline_approvals` data source or from an ADO notification), it sets the approval `status` (approved/rejected) and an optional `comment`.

### `betterado_pipeline_approvals` (data source)

Lists pending approvals for a project. Returns a set of `Approval` objects, each with its ephemeral `id`, pipeline reference, stage, step, instructions, and current status. Used to discover which approvals are outstanding before driving them via `betterado_pipeline_approval`.

## Declarative vs ephemeral state

### Declarative-manageable state (via `UpdateApprovals`)

The following fields represent the **only state that Terraform can declare** for a pipeline approval:

| Field | Type | Values | betterado attribute |
|---|---|---|---|
| `status` | `ApprovalStatus` | `approved`, `rejected` | `status` |
| `comment` | `string` | any string | `comment` |

`UpdateApprovals` accepts a slice of `Approval` objects with `id`, `status`, and optionally `comment`. betterado sets exactly these fields.

### Ephemeral-only operations (not declarative)

| Operation | Reason not declarative |
|---|---|
| `GetApproval` / `QueryApprovals` | Read-only operations; no state to declare |
| Approval creation | ADO creates approvals automatically when a pipeline run reaches a gated stage; they cannot be created by Terraform |
| Approval deletion/cancellation | ADO cancels approvals when the pipeline run completes or times out; betterado does not manage lifecycle teardown |

### Approval IDs are ephemeral — import is not supported

Approval IDs (`Approval.id`, a UUID) are **generated by ADO per pipeline run**. They are bound to a specific run of a specific pipeline and cease to be meaningful once the run completes. Consequently:

- `betterado_pipeline_approval` **cannot be imported** via `terraform import` — the approval ID from a previous run is no longer actionable.
- Every new pipeline run that requires approval generates a fresh approval ID, which must be discovered via `betterado_pipeline_approvals` (data source) or from an ADO event notification.
- The Terraform resource is **ephemeral by design**: it is created (approval decision set), and once the pipeline run concludes, the approval is no longer relevant. The resource is typically used in automation pipelines that self-approve.

## Not in scope

| Area | Reason |
|---|---|
| Approval policy configuration (`check_approval` settings: approvers list, instructions, min approvers) | Managed separately by `azuredevops_check_approval` in the `approvalsandchecks` package (see `docs/approvalsandchecks-gap-matrix.md`). That resource configures the **approval gate** on an environment/resource; `betterado_pipeline_approval` drives the **approval decision** on a specific run. |
| Other pipeline check types (branch control, business hours, exclusive lock, REST API, required template) | Managed by `azuredevops_check_*` resources in the `approvalsandchecks` package. |
| Pipeline run management (triggering runs, querying run status) | Out of scope for this initiative; covered by `azuredevops_build_*` resources. |
| Approval history / audit log | ADO does not expose a writable API for this; audit data is out of scope for Terraform management. |
