### 2.3 Filter types (ISubscriptionFilter polymorphism)

`Filter` is polymorphic — the `type` field discriminates between filter kinds. The API uses different concrete structs on the wire.

| Filter type (wire `type` value) | Go struct | Status | Rationale |
|---|---|---|---|
| `Expression` | `ExpressionFilter` → `ExpressionFilterModel` (clauses + groups) | **implement** | The standard user-facing filter for most event types. WI-2 must support this. |
| `RoleBased` | `RoleBasedFilter` (inclusions/exclusions of roles) | **out-of-scope** | Used for role-assignment subscriptions (e.g. reviewer assigned). Requires UI role enumeration; deferred. |
| `Actor` | `ActorFilter` (inclusions/exclusions of identities) | **out-of-scope** | Identity-specific subscriptions. Deferred; complex identity resolution. |
| `Block` | `BlockFilter` | **out-of-scope** | Internal/system filter type; not user-configurable. |
| `Artifact` | `ArtifactFilter` | **out-of-scope** | Used for "follow" subscriptions on specific artifacts. Niche use case; deferred. |
| `Unsupported` | `UnsupportedFilter` | **out-of-scope** | Placeholder for unknown types; never sent by client. |

**For WI-2:** implement `ExpressionFilter` only. `ExpressionFilterModel` contains `Clauses` (`[]ExpressionFilterClause`) with `fieldName`, `operator`, `value`, `logicalOperator`, `index` — all writable. The `groups` and `maxGroupLevel` fields describe nesting and are computed from the clause ordering.

### 2.4 Channel types (ISubscriptionChannel polymorphism)

`Channel` is polymorphic — discriminated by `type` string.

| Channel type (wire `type` value) | Go struct | Status | Rationale |
|---|---|---|---|
| `EmailHtml` | `EmailHtmlSubscriptionChannel` (`address`, `useCustomAddress`) | **implement** | Primary email delivery. `address` + `useCustomAddress` are writable. |
| `EmailPlaintext` | `EmailPlaintextSubscriptionChannel` (`address`, `useCustomAddress`) | **implement** | Plain-text email variant. Same schema as `EmailHtml`. |
| `User` | `UserSubscriptionChannel` (`address`, `useCustomAddress`) | **implement** | Delivers to the subscriber's default notification email. |
| `Group` | `GroupSubscriptionChannel` (`address`, `useCustomAddress`) | **implement** | Group delivery channel. |
| `UserSystem` | `UserSystemSubscriptionChannel` (`address`, `useCustomAddress`) | **out-of-scope** | Internal/system notifications; not user-created. |
| `Soap` | `SoapSubscriptionChannel` (`address`, `useCustomAddress`) | **out-of-scope** | Legacy SOAP endpoint; not a TF use case. |
| `ServiceBus` | `ServiceBusSubscriptionChannel` (`type` only) | **out-of-scope** | Azure Service Bus delivery; requires separate service hook plumbing. |
| `ServiceHooks` | `ServiceHooksSubscriptionChannel` (`type` only) | **out-of-scope** | Service hook delivery; separate provider concern (`azuredevops_servicehook_*`). |
| `MessageQueue` | `MessageQueueSubscriptionChannel` (`type` only) | **out-of-scope** | Internal message queue delivery. |
| `Block` | `BlockSubscriptionChannel` (`type` only) | **out-of-scope** | Blocks delivery; internal use. |

**For WI-2:** implement `EmailHtml`, `EmailPlaintext`, `User`, and `Group` channels. These cover all typical user-created subscriptions. Wire as a single `channel` block with `type` (required string enum) and optional `address` / `use_custom_address`.

## 4. NotificationSubscriptionTemplate — Triage

**Status: `betterado_notification_subscription_template` → out-of-scope for this initiative**

### Rationale

`NotificationSubscriptionTemplate` is returned by `GetSubscriptionTemplates` (GET only; no create/update/delete). It describes ADO's built-in notification templates that users can subscribe to:

| Field | JSON tag | Go type | Notes |
|---|---|---|---|
| `Description` | `description` | `*string` | Template description |
| `Filter` | `filter` | `*ISubscriptionFilter` | Pre-configured filter for this template |
| `Id` | `id` | `*string` | Template identifier (e.g. `ms.vss-code.git-pullrequest-created-subscription`) |
| `NotificationEventInformation` | `notificationEventInformation` | `*NotificationEventType` | Full event type metadata |
| `Type` | `type` | `*SubscriptionTemplateType` | `user` / `team` / `both` / `none` |

**Why out-of-scope:**
1. **Read-only API**: There are no create, update, or delete endpoints for templates. They are server-defined and cannot be managed by Terraform.
2. **Data source candidate only**: A future `betterado_notification_subscription_template` data source could expose template IDs and filter configurations to help users build subscriptions, but this is a convenience feature, not a required building block.
3. **Out of initiative scope**: This initiative (`INIT-2026-07-01-new-api-notification`) focuses on managing `NotificationSubscription` resources (CRUD). Template discovery is not required for the core subscription resource.
4. **Deferred to future initiative**: The data source could be added as a follow-on to provide ergonomic template-to-subscription workflows.
