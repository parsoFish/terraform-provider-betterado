## 1. API Surface Overview

The ADO Feature Management REST API (`_apis/featuremanagement/featureflags`) exposes two primary resources:

| ADO REST endpoint | SDK method | Purpose |
|---|---|---|
| `GET _apis/featuremanagement/featureflags/{featureId}` | `GetFeature` | Retrieve a single feature definition |
| `GET _apis/featuremanagement/featureflags` | `GetFeatures` | List all feature definitions |
| `GET _apis/featuremanagement/featureflags/{featureId}/{userScope}` | `GetFeatureState` | Get host/user-scoped state |
| `PATCH _apis/featuremanagement/featureflags/{featureId}/{userScope}` | `SetFeatureState` | Set host/user-scoped state |
| `GET _apis/featuremanagement/featureflags/{featureId}/{userScope}/{scopeName}/{scopeValue}` | `GetFeatureStateForScope` | Get named-scope state (e.g. project) |
| `PATCH _apis/featuremanagement/featureflags/{featureId}/{userScope}/{scopeName}/{scopeValue}` | `SetFeatureStateForScope` | Set named-scope state (e.g. project) |
| `POST _apis/featuremanagement/featurestates` | `QueryFeatureStates` | Batch query effective states |
| `POST _apis/featuremanagement/featurestates/{userScope}` | `QueryFeatureStatesForDefaultScope` | Batch query for default scope |
| `POST _apis/featuremanagement/featurestates/{userScope}/{scopeName}/{scopeValue}` | `QueryFeatureStatesForNamedScope` | Batch query for named scope |

All methods are marked `[Preview API]` at version `7.1-preview.1`.

## 2. ContributedFeature Field Matrix

`ContributedFeature` is the **definition** of a feature (its metadata, not its enabled/disabled/undefined state).

| Field | ADO Go type | Writable? | TF attribute status | Notes |

| `id` | `*string` | No | `feature_id` — Required, ForceNew | Contribution ID (e.g. `ms.vss-work.agile`). User provides on create; becomes the resource ID. |
| `name` | `*string` | No | Computed (read-only) | Human-readable display name; set by ADO, not the user. |
| `description` | `*string` | No | Computed (read-only) | Feature description; server-side metadata. |

## 3. ContributedFeatureState Field Matrix

`ContributedFeatureState` models the **on/off/unset** state of a feature at a given scope. This is the primary resource being managed by `betterado_feature_flag`.

| Field | ADO Go type | Writable? | TF attribute status | Notes |
|---|---|---|---|---|
| `featureId` | `*string` | Yes — key | `feature_id` — Required, ForceNew | Contribution ID of the feature being managed. |
| `state` | `*ContributedFeatureEnabledValue` | Yes | `state` — Required | One of `enabled`, `disabled`, `undefined`. See §4 for semantics. |
| `scope` | `*ContributedFeatureSettingScope` | Yes — derived | Encoded in `user_scope`, `scope_name`, `scope_value` | The scope struct is constructed from the three TF attributes; not exposed as a nested block. |
| `overridden` | `*bool` | No | Computed (read-only) | True when an ADO `overrideRule` is controlling the state, preventing user override. |
| `reason` | `*string` | No | Computed (read-only) | Reason text set by an override rule; server-supplied. |

**Summary — ContributedFeatureState:** 2 writable fields (`featureId`, `state`) + 3 scope routing fields / 2 read-only.

## 4. Available Scopes

The API routes feature state via a combination of `userScope`, `scopeName`, and `scopeValue` path parameters (see `GetFeatureStateForScope` / `SetFeatureStateForScope`).

### 4.1 Scope Dimensions

| Dimension | Parameter | Values | Notes |
|---|---|---|---|
| `userScope` | `UserScope` | `"host"` | Applies to all users in the organisation (org-level or project-level policies). |
| `userScope` | `UserScope` | `"me"` | Applies to the current user only (personal preference). **Not in scope — see §6.** |
| `scopeName` | `ScopeName` | `"project"` | Used together with `userScope="host"` to scope to a specific project. |
| `scopeValue` | `ScopeValue` | `<project UUID>` | The GUID of the target project when `scopeName="project"`. |
| `scopeName` | `ScopeName` | _(omitted)_ | Omitting `scopeName`/`scopeValue` with `userScope="host"` gives org/host-wide state. |

### 4.2 Scope Combinations for `betterado_feature_flag`

| Scope | `user_scope` | `scope_name` | `scope_value` | SDK method |
|---|---|---|---|---|
| **Host (org-wide)** | `"host"` | _(empty)_ | _(empty)_ | `SetFeatureState` |
| **Project** | `"host"` | `"project"` | `<project_id>` | `SetFeatureStateForScope` |
| **User** | `"me"` | _(empty)_ | _(empty)_ | `SetFeatureState` — **Out of scope (§6)** |

The `ContributedFeatureSettingScope` struct carries `{settingScope, userScoped}`:
- `userScoped: false` → host-scoped (org or project)
- `userScoped: true` → user-scoped personal setting

## 5. State Values

The `ContributedFeatureEnabledValue` enum has three values:

| API string | Go constant | Meaning | Destroy semantics |
|---|---|---|---|
| `"enabled"` | `ContributedFeatureEnabledValueValues.Enabled` | Feature is explicitly enabled at this scope. | On `destroy`: reset to `"undefined"` (defer to default). |
| `"disabled"` | `ContributedFeatureEnabledValueValues.Disabled` | Feature is explicitly disabled at this scope. | On `destroy`: reset to `"undefined"`. |
| `"undefined"` | `ContributedFeatureEnabledValueValues.Undefined` | No explicit setting at this scope; effective value falls back to the feature's `defaultState` or a parent scope. | On `destroy`: no-op (already the unset state). |

**`undefined` destroy semantics:** When the resource is destroyed, the provider should `PATCH` the feature state to `undefined` rather than `enabled`, so the org's default takes over rather than leaving the feature in any particular state. This mirrors how IaC lifecycle should work: destroy = remove management, not reset to on.

**`undefined` in config:** Allowing `state = "undefined"` in the TF config is intentionally allowed so that callers can ensure a feature has *no* explicit override at a given scope (useful for "let the org default apply").

## 6. Differences from `betterado_project_features`

`betterado_project_features` (`resource_project_features.go`) and the proposed `betterado_feature_flag` both use the featuremanagement SDK, but they serve different purposes:

| Dimension | `betterado_project_features` | `betterado_feature_flag` (proposed) |
|---|---|---|
| **Resource type** | Composite "all project features as a map" | Single feature-state tuple |
| **Endpoint used** | `QueryFeatureStates` (batch POST) for reads; `SetFeatureStateForScope` for writes | `GetFeatureStateForScope` for reads; `SetFeatureStateForScope` or `SetFeatureState` for writes |
| **Feature IDs managed** | Fixed hardcoded set of 5: `ms.vss-work.agile`, `ms.vss-code.version-control`, `ms.vss-build.pipelines`, `ms.vss-test-web.test`, `ms.azure-artifacts.feature` | Any valid feature contribution ID |
| **Scopes available** | Project-scoped only (`userScope="host"`, `scopeName="project"`) | Host-wide or project-scoped (user-scoped out of scope — §6.2) |
| **Terraform identity** | `project_id` as resource ID — one resource manages all 5 features for a project | `<feature_id>/<user_scope>[/<scope_name>/<scope_value>]` as composite ID — one resource per feature×scope |
| **User-facing attribute** | `features = { boards = "enabled", pipelines = "disabled", … }` map | `feature_id`, `user_scope`, `scope_name`, `scope_value`, `state` flat attributes |
| **Destroy behaviour** | Re-enables all managed features (reset to `enabled`) | Resets state to `undefined` (defer to default) |
| **ADO API path** | Calls the composite `_apis/featuremanagement/featureflags/_apis/projects/{id}/featureflags` endpoint via the query method | Calls `_apis/featuremanagement/featureflags/{featureId}/{userScope}[/{scopeName}/{scopeValue}]` directly |

### 6.1 Why two resources?

`betterado_project_features` exists as a high-level convenience resource for the most common project feature toggles. It is optimised for the "I want boards/pipelines/repos on or off" use case with a clean map syntax.

`betterado_feature_flag` targets the full generic surface: arbitrary feature IDs, host-level toggles, and finer-grained per-scope control. It is the IaC primitive for managing any of the ~200+ ADO feature flags without requiring a hardcoded mapping in the provider.

### 6.2 Avoiding overlap

Both resources can coexist in the same configuration targeting the same project features as long as the operator does not create a conflict (both managing `ms.vss-work.agile` for the same project). This is a runtime concern, not a schema concern — the provider will warn on plan if a feature already has an explicit state that differs from the requested value.

## 7. Non-Goals (Out of Scope for This Initiative)

### 7.1 User-scoped feature flags

`userScope = "me"` flags express personal preferences for the **authenticated user running Terraform**. These are:

- **Non-declarative** — the "user" changes depending on who runs `terraform apply` (CI bot vs individual engineer).
- **Not stable** — ADO personal settings can be reset by org policy changes outside IaC control.
- **No meaningful lifecycle** — a `destroy` would change the individual's personal ADO experience, not any shared resource state.

> **Decision:** User-scoped flags (`userScope = "me"`) are explicitly excluded from `betterado_feature_flag`. The resource will validate that `user_scope` is `"host"` and return an error if `"me"` is supplied.

### 7.2 Feature definitions as a managed resource

`ContributedFeature` (the definition of a feature, with `id`, `name`, `description`, `scopes`, etc.) is **read-only metadata** contributed by ADO extensions and built-in services. It cannot be created, updated, or deleted through the Feature Management REST API. A data source (`data.betterado_feature_flag`) that reads definition metadata is a future candidate but is not part of this initiative.

### 7.3 Batch / composite state management

`QueryFeatureStates`, `QueryFeatureStatesForDefaultScope`, and `QueryFeatureStatesForNamedScope` enable efficient batch reads. The `betterado_feature_flag` resource uses single-feature GET/PATCH semantics (one TF resource = one feature×scope). Batch state endpoints may be used internally for optimisation (e.g. plan-time pre-fetch) but are not exposed as a resource type.

### 7.4 Override rules and computed-only fields

Fields `overridden` and `reason` on `ContributedFeatureState` are surfaced as Computed read-only attributes so operators can inspect whether a feature is being held by an ADO override rule. They are not writable.

## 8. Proposed `betterado_feature_flag` Schema (Preview)

Based on the above analysis, the `betterado_feature_flag` resource should expose:

| TF attribute | Schema type | Required? | Computed? | ForceNew? | Maps to ADO field |
|---|---|---|---|---|---|
| `feature_id` | `TypeString` | Yes | No | Yes | `ContributedFeatureState.featureId` / route param `featureId` |
| `user_scope` | `TypeString` | Yes | No | Yes | Route param `userScope`; validated as `"host"` only |
| `scope_name` | `TypeString` | No | No | Yes | Route param `scopeName`; e.g. `"project"` |
| `scope_value` | `TypeString` | No | No | Yes | Route param `scopeValue`; e.g. project GUID |
| `state` | `TypeString` | Yes | No | No | `ContributedFeatureState.state`; validated enum: `enabled`, `disabled`, `undefined` |
| `overridden` | `TypeBool` | No | Yes | No | `ContributedFeatureState.overridden`; read-only |
| `reason` | `TypeString` | No | Yes | No | `ContributedFeatureState.reason`; read-only |

**Resource ID format:** `<feature_id>/<user_scope>[/<scope_name>/<scope_value>]`
Example: `ms.vss-work.agile/host/project/00000000-0000-0000-0000-000000000001`

**Import format:** Same as resource ID.
