# ADO Test REST API v7.1 — Gap Matrix

> **Initiative:** `INIT-2026-07-01-new-api-test`
> **Generated by:** WI-1 dev-loop
> **ADO SDK version:** `github.com/microsoft/azure-devops-go-api/azuredevops/v7/test`
> **SDK mock source:** `azdosdkmocks/test_sdk_mock.go`
> **REST API surface:** `_apis/test/*` (legacy v7.1) + `_apis/testplan/*` (modern; not in Go SDK vendor here)

---

## How to read this matrix

| Status | Meaning |
|---|---|
| `implement-as-resource` | Has stable Create + Update + Delete lifecycle → full Terraform resource. Idempotent; exists between `apply` runs. |
| `implement-as-data-source` | Meaningful read but creation is external, ephemeral, or managed outside Terraform. Surfaced as `data "betterado_*"`. |
| `read-only` | The SDK exposes only Get operations; no Create or Delete available. Not actionable by Terraform. |
| `out-of-scope` | Execution-orchestration (queuing/running tests) or binary-payload operations explicitly excluded by the initiative; would be anti-patterns in declarative IaC. |

## 3. Declarative-vs-Ephemeral Decision Framework

The central question for every ADO Test API type is: **"Does this object exist between Terraform runs?"**

### 3.1 Declarative objects (stable between `apply` runs)

These objects are created by engineers at project setup time, persist indefinitely, and can be idempotently re-applied:

- **Test Plan** — created once per project/release cycle; named, versioned, lives until archived.
- **Test Suite** — hierarchical child of a plan; stable container for test cases.
- **Test Configuration** — named browser/OS/env tuple; reused across many plans.
- **Test Variable** — named parameter (e.g., `Browser`) whose values (e.g., `Chrome`, `Firefox`) drive configurations.
- **Result Retention Settings** — a singleton project-level policy (like a firewall rule).

These map naturally to Terraform resources: `terraform apply` creates them, `terraform destroy` removes them, `terraform plan` detects drift.

### 3.2 Ephemeral objects (created by CI pipelines at execution time)

These objects are **produced by test execution** and exist only as historical records:

- **Test Run** — the output of a pipeline step that ran `vstest.console.exe` or pytest. A new run is created for every pipeline run. There is no single "authoritative" run that Terraform could manage — a second `apply` would create a second run, making the resource non-idempotent. The lifecycle is owned entirely by the CI system.
- **Test Result** — a sub-record of a test run recording one test case's outcome (Pass/Fail/Skip). Results are written by the test runner post-execution. Creating results from Terraform would inject synthetic data into the ADO test reporting system, violating data integrity.
- **Test Iteration** — a sub-record within a result (for data-driven/parameterised tests). Server-generated.

**Why data-source-only for test runs and results:**
A `data "betterado_test_run"` can query the most recent runs for a build definition or pipeline, enabling downstream Terraform to gate on test outcomes (e.g., "only provision staging if the last run passed"). This is the legitimate IaC use case: **reading** execution evidence, not **creating** it.

### 3.3 Out-of-scope (execution-orchestration)

Test sessions and attachments are transient artefacts of live test execution with binary payloads or ephemeral lifecycles that have no declarative IaC equivalent. Even a data source would provide limited value (no stable identifier for the "current" session or attachment).

## 4. WI Implementation Roadmap

The following work items are expected downstream of this gap matrix:

| WI | Resource(s) | Notes |
|---|---|---|
| WI-2 | `betterado_test_plan` (resource) | Core container. Requires `_apis/testplan/Plans` — not in legacy test SDK; needs testplan client wiring. |
| WI-3 | `betterado_test_suite` (resource) | Hierarchical suites under a plan. Use `_apis/testplan/Suites`. |
| WI-4 | `betterado_test_configuration` (resource), `betterado_test_variable` (resource) | Stable named configuration objects. `_apis/testplan/Configurations` + `_apis/testplan/Variables`. |
| WI-5 | `betterado_test_result_retention_settings` (resource) | Singleton project-level policy. `_apis/test/resultretentionsettings` — `Get` + `Update` only (no create/delete). |
| WI-6 | `data.betterado_test_run` (data source) | Query test runs by build/pipeline. `_apis/test/runs` + `QueryTestRuns`. |
| WI-7 | `data.betterado_test_result` (data source) | Query test results for a given run. `_apis/test/runs/{runId}/results`. |

> **Note:** Test Case management is intentionally delegated to the existing `betterado_workitem` resource (test cases are work items). Suite membership (associating a test case with a suite) is implemented as part of WI-3 (`betterado_test_suite` manages its child test case IDs).

## 6. Appendix: ADO REST API Surface vs SDK

The Go SDK `test` package (legacy, `c2aa639c-3ccc-4740-b3b6-ce2a1e1d984e` resource area) covers `_apis/test/*`. The modern `testplan` package (`_apis/testplan/*`) is **not vendored** in this repository and is required for full plan/suite/configuration CRUD. WI-2 through WI-4 must vendor the testplan client or call the REST API directly.

Key REST surfaces not covered by the legacy SDK mock:
- `_apis/testplan/Plans` — Create/Update/Delete test plans
- `_apis/testplan/Suites` — Create/Update/Delete test suites
- `_apis/testplan/Configurations` — Create/Update/Delete test configurations
- `_apis/testplan/Variables` — Create/Update/Delete test variables
- `_apis/testplan/Points` — Modern test point query (supersedes `_apis/test/plans/{planId}/suites/{suiteId}/points`)
