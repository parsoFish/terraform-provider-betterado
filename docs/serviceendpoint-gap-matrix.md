## Overview

The ADO Service Endpoint REST API v7.1 uses a **generic envelope** — the `ServiceEndpoint` struct — for all endpoint types. Type-specific credential fields are stored in `authorization.parameters` (a `map[string]string`) and additional metadata in `data` (also a `map[string]string`). The TF provider exposes each endpoint type as a separate resource, surfacing the relevant keys from those maps as typed schema attributes.

### Core ServiceEndpoint struct (SDK model)

| Field | ADO type | Notes |
|---|---|---|
| `id` | `*uuid.UUID` | Computed; set as resource ID |
| `name` | `*string` | covered as `service_endpoint_name` in every resource |
| `description` | `*string` | covered as `description` in every resource (base schema) |
| `type` | `*string` | covered internally; not exposed directly (except in `generic_v2`) |
| `url` | `*string` | covered per-resource (varies) |
| `authorization` | `*EndpointAuthorization` | covered as `authorization` computed map + resource-specific fields |
| `authorization.parameters` | `*map[string]string` | Type-specific credential keys flattened into resource schema |
| `authorization.scheme` | `*string` | Set internally per resource; not exposed except in `generic_v2` |
| `data` | `*map[string]string` | Type-specific extra data; incompletely exposed per resource |
| `isReady` | `*bool` | **Missing** | Read-only; endpoint readiness status |
| `isShared` | `*bool` | **Missing** | Read-only; whether shared across projects |
| `owner` | `*string` | **Missing** | Read-only; `"library"` or `"agentcloud"` |
| `createdBy` | `*webapi.IdentityRef` | **Missing** | Read-only computed metadata |
| `serviceEndpointProjectReferences` | `*[]ServiceEndpointProjectReference` | covered internally; `project_id` and cross-project sharing via `shared_project_ids` in `generic_v2` only |
| `administratorsGroup` | `*webapi.IdentityRef` | **Missing** | Deprecated; out of scope |
| `groupScopeId` | `*uuid.UUID` | **Missing** | Deprecated; out of scope |
| `readersGroup` | `*webapi.IdentityRef` | **Missing** | Read-only; managed by ADO |
| `operationStatus` | `interface{}` | **Missing** | Read-only; transient error message |

**Base schema fields (shared by ALL endpoint resources):**

| TF attribute | Maps to | R/O/C | Notes |
|---|---|---|---|
| `project_id` | `serviceEndpointProjectReferences[0].projectReference.id` | Required | ForceNew |
| `service_endpoint_name` | `name` | Required | |
| `description` | `description` (via `ServiceEndpointProjectReference.description`) | Optional | Default `"Managed by Terraform"` |
| `authorization` | `authorization.parameters` (Computed map) | Computed | Read-back of auth params |

## 3. Credential-Rotation-Only Fields: Deferred Rationale

The following fields are **explicitly deferred** across all endpoint types because they are **credential-rotation-only**:

**Pattern:** ADO REST API returns `null` / empty string for all secret/password/token/key fields in GET responses. The provider must keep the last-written value in state to detect changes (plan-time drift detection for credential rotation). These fields:
1. Cannot be verified server-side on read (no plaintext returned)
2. Are Sensitive — must not appear in plan output

### 5.3 Conclusion

All 42 endpoint type resources (30+ distinct ADO endpoint types) have been surveyed. The provider's schema coverage is **comprehensive for non-credential fields**. The only writable gaps that are not credential-rotation-only are:

1. `octopus_deploy.api_key` missing `Sensitive: true` (schema quality; not a functional gap)
2. `kubernetes` `namespace` for `service_account` auth type (low-priority; ADO defaults to Kubernetes default namespace)
3. `workload_identity_federation_subject` on Azure resources (read-only advisory computed attribute; useful for WIF trust setup)
4. `shared_project_ids` on non-generic typed resources (cross-project sharing; only in `generic_v2` today)

All credential fields (`password`, `token`, `api_key`, etc.) are **intentionally deferred** as credential-rotation-only: ADO never returns secret values in GET responses, so these fields can only be tracked via state, not read back from the API. This is the correct and intentional design pattern for all service endpoint resources.
