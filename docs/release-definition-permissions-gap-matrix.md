## 1. Namespace Overview

The `ReleaseManagement2` security namespace governs access to classic release definitions
(the VSRM pipeline engine, as distinct from the newer YAML multi-stage pipelines which use
a different namespace).  Every permission bit is a bitmask integer that ADO stores in the
`Allow` and `Deny` fields of an `AccessControlEntry` (ACE).  All bits in this namespace
are writable via `SetAccessControlEntries` — see §2 for details.

| `DeleteReleases` | 4 | Yes | Delete a release instance | ✅ `TestAccReleaseDefinitionPermissions_SetPermissions`, `TestAccReleaseDefinitionPermissions_UpdatePermissions` |
| `ManageReleasesSettings` | 8 | Yes | Manage release-level settings on a definition | No |
| `ViewReleasePipeline` | 16 | Yes | View the release pipeline definition (read the definition JSON) | No |
| `EditReleasePipeline` | 32 | Yes | Create, edit, or save a release definition | No |
| `DeleteReleasePipeline` | 64 | Yes | Delete a release definition | No |
| `ManageReleaseApprovers` | 128 | Yes | Add or remove approvers on a release environment | No |
| `CreateReleases` | 256 | Yes | Trigger a new release from a definition | ✅ `TestAccReleaseDefinitionPermissions_SetPermissions`, `TestAccReleaseDefinitionPermissions_UpdatePermissions` |
| `QueueRelease` | 512 | Yes | Queue a release / deploy to a specific environment | No |
| `AdministerReleasePermissions` | 1024 | Yes | Administer release permissions — manage ACEs for the definition | No |
| `ManageDeployments` | 4096 | Yes | Manage deployments: view and approve stage gates | No |

> **All 12 bits are Writable=yes.** ADO's `SetAccessControlEntries` API accepts every bit
> listed above for the `ReleaseManagement2` namespace.  There are no read-only permission
> bits in this namespace.

## 3. Token Format

ACL tokens in the `ReleaseManagement2` namespace use a two-level hierarchy:

| Scope | Token format | Example |
|---|---|---|
| Project-level (all definitions in project) | `{projectId}` | `21cff396-a36f-4d05-bccf-91e3a2a8b4bb` |
| Definition-level (single release definition) | `{projectId}/{releaseDefinitionId}` | `21cff396-a36f-4d05-bccf-91e3a2a8b4bb/7` |

**Source:** confirmed via live ADO probe on 2026-06-06 against org `davidgparsonson`
(documented in `resource_release_definition_permissions.go` header comments).

> **Note:** The `ReleaseManagement2/Project/{projectId}/{definitionId}` format sometimes
> cited in ADO documentation was **not observed** in the live API.  The actual format is the
> simpler `{projectId}/{releaseDefinitionId}` — identical in structure to the `Build`
> namespace.

## 4. Example HCL — All Writable Permission Keys

```hcl
resource "betterado_release_definition_permissions" "example" {
  project_id            = azuredevops_project.example.id
  principal             = data.betterado_group.readers.id
  release_definition_id = betterado_release_definition.example.id

  permissions = {
    ViewReleases                 = "Allow"
    EditReleaseEnvironment       = "Allow"
    DeleteReleases               = "Deny"
    ManageReleasesSettings       = "Deny"
    ViewReleasePipeline          = "Allow"
    EditReleasePipeline          = "Deny"
    DeleteReleasePipeline        = "Deny"
    ManageReleaseApprovers       = "Deny"
    CreateReleases               = "Allow"
    QueueRelease                 = "Allow"
    AdministerReleasePermissions = "Deny"
    ManageDeployments            = "Allow"
  }
}
```

Valid values for each permission key: `"Allow"`, `"Deny"`, `"NotSet"` (case-insensitive
— the provider normalises all values to lowercase in state).
