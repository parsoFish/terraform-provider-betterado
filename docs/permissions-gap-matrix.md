## 1. Overview

All 13 resources in this package are **thin wrappers** around a shared base implementation in `azuredevops/internal/service/permissions/utils/`. Each resource:

1. Defines a resource-specific schema (resource identifier fields + the common base schema)
2. Implements a `create<X>Token` function that constructs the ADO security token for the namespace
3. Delegates all ACL read/write operations to `securityhelper.{New,Set,Get}PrincipalPermissions`

### Common base schema (all resources)

Every resource inherits the following fields from `CreatePermissionResourceSchema`:

| TF field | API field / concept | Writable? | Notes |
|---|---|---|---|
| `principal` | Subject descriptor → resolved to identity descriptor for `AccessControlEntry.Descriptor` | Yes | Required; `ForceNew` |
| `replace` | `merge` flag on `SetAccessControlEntries` (inverted: `merge = !replace`) | Yes | Optional; default `true` |
| `permissions` | `AccessControlEntry.Allow` + `AccessControlEntry.Deny` (bitmask encoded as `allow`/`deny`/`notset` strings) | Yes | Required TypeMap |

### Writable gaps — resolution decisions

| Gap | Affected resources | Decision | Rationale |
|---|---|---|---|
| `AccessControlList.InheritPermissions` | All 13 resources | **Deferred** | The `InheritPermissions` flag on an ACL token controls whether the token inherits permissions from parent tokens. Exposing it would allow practitioners to explicitly disable inheritance (e.g. lock down a specific build folder without inheriting project-level permissions). This is a medium-complexity change requiring a new `inherit_permissions` attribute in the base schema and a separate ACL write to `UpdateAccessControlList`. Deferred to a future WI as part of the framework migration. |
